1 دامنه‌ی ERP و گردش‌کارها

ERP یک داشبورد با چند فرم نیست؛ چند واحد کاری باید روی داده‌ی مشترک و تراکنش‌های قابل ردیابی کار کنند. دامنه‌ی MVP این سند شامل موارد زیر است:

حوزهقابلیت‌های MVPخروجی مهم
پایه و دسترسیشرکت، شعبه، انبار، کاربر، نقش و مجوزداده‌ی هر شرکت از شرکت دیگر جدا بماند
کاتالوگ و طرف‌حسابکالا/خدمت، دسته، واحد، مشتری، تأمین‌کنندهSKU یکتا در محدوده‌ی شرکت، فعال/غیرفعال‌سازی به‌جای حذف
انبارمانده، رزرو، رسید، حواله، اصلاح و انتقالدفتر گردش غیرقابل‌ویرایش و تطبیق با مانده
خریدسفارش خرید، تأیید، دریافت کامل/جزئی، فاکتور تأمین‌کنندهموجودی بیشتر و بدهی قابل پرداخت
فروشسفارش، رزرو، ارسال کامل/جزئی، فاکتور، دریافت وجهموجودی کمتر، طلب مشتری و درآمد ثبت‌شده
مالیحساب‌ها، دریافت/پرداخت، دفتر روزنامه و تراز آزمایشیهر سند ثبت‌شده تراز بدهکار/بستانکار داشته باشد
کنترل و گزارشAudit log، داشبورد، مانده‌ی انبار و فروش/خریدمشخص باشد چه کسی، چه چیزی و چه زمانی را تغییر داده

دو مسیر اصلی کسب‌وکار:

Procure-to-Pay: Purchase Order → Approval → Goods Receipt → Supplier Invoice → Payment → Journal
Order-to-Cash:  Sales Order → Stock Reservation → Shipment → Customer Invoice → Receipt → Journal
مرزبندی مهم: خرید/فروش/انبار در این MVP یک modular monolith است؛ یعنی یک API و یک دیتابیس با ماژول‌های جدا. Micro-frontend و microservice را از روز اول اضافه نکنید؛ پیچیدگی deploy، تراکنش و مشاهده‌پذیری را بالا می‌برند و برای تیم کوچک معمولاً سودی ندارند.

2 معماری و تصمیم‌های پایه

Browser (React SPA, RTL)
        │ HTTPS / JSON  /api/v1
        ▼
NestJS API ── Auth / Permission / Audit / Validation
        │
        ├── Catalog ── Customers / Suppliers / Products
        ├── Inventory ── Balances / Reservations / Movements
        ├── Purchasing ── Orders / Receipts
        ├── Sales ── Orders / Shipments
        └── Finance ── Invoices / Payments / Journal
        │ Prisma (transaction boundary)
        ▼
PostgreSQL  ── migrations, indexes, backups
  • مرز ماژول‌ها: controller فقط HTTP را ترجمه کند؛ قانون کسب‌وکار در service/use-case بماند؛ هر ماژول API عمومی خودش را داشته باشد.
  • منبع حقیقت: PostgreSQL. React هیچ‌وقت مستقیماً به دیتابیس وصل نمی‌شود و مدل‌های Prisma را به مرورگر نمی‌فرستیم.
  • تراکنش: تغییر وضعیت سند، تغییر مانده‌ی انبار، ساخت movement، ثبت Journal و audit مرتبط باید در یک تراکنش واحد یا با الگوی outbox کنترل‌شده انجام شود.
  • مقدار مالی: از Decimal در DB و رشته‌ی decimal در ورودی/خروجی استفاده کنید؛ عدد اعشاری JavaScript را برای جمع پول به کار نبرید.
  • زمان: timestampها در DB به UTC ذخیره شوند؛ timezone و ارز پیش‌فرض در تنظیمات شرکت باشند.
  • حذف: سند ثبت‌شده پاک نشود؛ با لغو/برگشت و سند معکوس اصلاح شود. کالا و کاربر استفاده‌شده در سابقه archive شوند، نه hard-delete.

3 ساختار Nx Monorepo

ساختار زیر ماژول‌های بک‌اند را از کد UI و قراردادهای مشترک جدا می‌کند. نام پوشه‌ها را در Nx با tagهای scope محدود کنید.

erp-platform/
├── apps/
│   ├── backend/                 # NestJS REST API
│   ├── frontend/                # React + Vite ERP console
│   └── frontend-e2e/            # Playwright scenarios
├── libs/
│   ├── shared/
│   │   ├── api-contracts/       # type/schemaهای عمومی؛ بدون وابستگی به Prisma/Nest
│   │   └── config/              # تنظیمات مشترک قابل انتشار
│   ├── backend/
│   │   ├── database/            # Prisma schema, migrations, PrismaService
│   │   ├── auth/                # login, session, guards, permissions
│   │   ├── audit/               # audit log
│   │   ├── catalog/             # products, categories, customers, suppliers
│   │   ├── inventory/           # balances, reservations, movements
│   │   ├── purchasing/          # purchase orders, goods receipts
│   │   ├── sales/               # sales orders, shipments
│   │   └── finance/             # invoices, payments, journal, reports
│   └── frontend/
│       ├── api-client/          # typed HTTP client
│       ├── ui/                  # shared controls, tables, dialogs
│       ├── auth/                # session and permission-aware navigation
│       └── features/            # feature UI grouped by domain
├── prisma.config.ts
├── docker-compose.yml
├── .env.example
└── nx.json / package.json / tsconfig.base.json
قانون import در Nx: scope:backend فقط به scope:backend و scope:shared وابسته شود؛ scope:frontend فقط به frontend/shared. Frontend نباید هیچ library بک‌اند یا Prisma را import کند. قانون دقیق tagها را مطابق نسخه‌ی Nx و eslint.config.mjs همین repo تنظیم کنید.

4 ساخت workspace و اپ‌ها

از Node LTS پشتیبانی‌شده توسط نسخه‌ی Nx انتخابی استفاده کنید و نسخه‌ی پکیج‌ها را با lockfile ثابت نگه دارید. دستورهای generator بین majorهای Nx ممکن است کمی فرق کنند؛ قبل از اجرا npx nx list @nx/nest و npx nx list @nx/react را ببینید.

node -v
npm -v
docker --version
docker compose version

npx create-nx-workspace@latest erp-platform --preset=apps --packageManager=npm --nxCloud=skip
cd erp-platform

npx nx add @nx/nest
npx nx g @nx/nest:app backend

npx nx add @nx/react
npx nx g @nx/react:app frontend --bundler=vite --routing=true --style=css

npx nx show projects

اگر generator نسخه‌ی Nx شما نام اپ را با مسیر می‌خواهد، از راهنمای همان generator استفاده کنید؛ هدف نهایی این است که پروژه‌ها در apps/backend و apps/frontend ساخته شوند. libهای دامنه را با generator Nx بسازید تا project configuration و path alias هم ایجاد شوند، نه با پوشه‌سازی دستی.

npx nx g @nx/js:lib libs/backend/database --importPath=@erp/backend-database --unitTestRunner=vitest
npx nx g @nx/js:lib libs/backend/inventory --importPath=@erp/backend-inventory --unitTestRunner=vitest
npx nx g @nx/js:lib libs/backend/sales --importPath=@erp/backend-sales --unitTestRunner=vitest
این commandها نقطه‌ی شروع‌اند، نه تضمین نام option برای همه‌ی نسخه‌های Nx. اگر generator شما از positional name مثل backend-inventory استفاده می‌کند، نام را به همان نحو وارد کنید و پوشه‌ی مقصد را با --directory تعیین کنید. بعد از تولید، هر پروژه را با npx nx show project <name> بررسی کنید.

5 PostgreSQL، Docker و تنظیمات

برای توسعه، PostgreSQL را در Docker اجرا کنید؛ API و UI را با Nx روی سیستم اجرا کنید تا hot reload سریع بماند.

فایل docker-compose.yml در ریشه:

services:
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-erp_user}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-local_only_change_me}
      POSTGRES_DB: ${POSTGRES_DB:-erp_db}
    ports:
      - "5432:5432"
    volumes:
      - erp_pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  erp_pgdata:

فایل .env.example را بسازید و آن را به .env کپی کنید. فایل واقعی را commit نکنید:

6 مدل داده‌ی ERP با Prisma

این schema یک هسته‌ی دامنه‌ای قابل توسعه است: شرکت و دسترسی، کاتالوگ، مانده و دفتر حرکت، سفارش و اسناد دریافت/ارسال، فاکتور/پرداخت و دفتر حسابداری. مدل‌ها عمداً همه‌ی قواعد را در constraint دیتابیس جا نمی‌دهند؛ اعتبارسنجی بین‌شرکتی، تراز سند و transitionهای وضعیت باید در service هم کنترل شود.

در Prisma 7+ فایل schema می‌تواند URL اتصال را از prisma.config.ts بگیرد. اگر major دیگری انتخاب کرده‌اید، generator/provider و محل DATABASE_URL را مطابق مستندات همان major هماهنگ کنید.

نکته‌ی مهم درباره‌ی prisma/config: این یک فایل یا پوشه در پروژه نیست و پکیج جداگانه‌ای هم نیست؛ یک import از package npm به نام prisma است. این الگو مخصوص Prisma 7 است. دستورهای نصب را از ریشه‌ی monorepo، همان‌جایی که package.json و prisma.config.ts قرار می‌گیرند، اجرا کن؛ بعد TypeScript Server ادیتور را restart کن.

برای نسخه‌ی نمونه‌ی این راهنما، اول Prisma CLI و Client را نصب کن:

8 احراز هویت، شرکت و RBAC

  • رمز عبور را با Argon2id یا الگوریتم امن پشتیبانی‌شده hash کنید؛ هیچ‌وقت plaintext یا hash قابل بازیابی ذخیره نشود.
  • Access token کوتاه‌عمر باشد. Refresh token چرخشی و hash‌شده در RefreshSession نگهداری شود و هنگام logout/reuse مشکوک revoke شود.
  • برای SPA ترجیحاً refresh token را در cookie با HttpOnly; Secure; SameSite نگه دارید و در صورت نیاز حفاظت CSRF اضافه کنید؛ token بلندمدت را در localStorage نگذارید.
  • مجوز نمونه: catalog.products.read، catalog.products.write، inventory.adjust، sales.order.approve، finance.invoice.post، admin.users.manage.
  • هر درخواست باید کاربر، شرکت فعال و permission را در سمت سرور بررسی کند. مخفی کردن دکمه در React کنترل دسترسی نیست.
  • همه‌ی queryهای دامنه‌ای با companyId scope شوند؛ شناسه‌ی رکورد از URL به‌تنهایی مجوز دسترسی نمی‌دهد. تغییر شرکت فعال هم باید membership کاربر را verify کند.
  • ورودی‌ها allowlist/validate شوند؛ rate limit روی login، محدودیت تلاش، log امن و حذف password/token از log الزامی است.
تست امنیت بحرانی: کاربر شرکت A نباید با دانستن ID سند شرکت B بتواند آن را بخواند، ویرایش کند یا در گزارش ببیند. این تست را برای هر ماژول و هر query حساس بنویسید.

11 قواعد و تراکنش‌های انبار

قاعده‌ی پایه: available = onHand - reserved. InventoryMovement دفتر تغییرناپذیر است؛ StockBalance برای خواندن سریع نگهداری می‌شود و باید با جمع movementها قابل تطبیق باشد.

  • ورود از رسید خرید مقدار مثبت دارد؛ ارسال فروش مقدار منفی؛ انتقال بین دو انبار دو movement هم‌زمان (خروج و ورود) می‌سازد.
  • اصلاح دستی موجودی فقط با permission، دلیل، مرجع و audit انجام شود؛ مقدار قبلی را overwrite نکنید.
  • برای confirmation سفارش فروش، موجودی قابل‌دسترس را رزرو کنید. هنگام لغو، reservation آزاد شود؛ هنگام ارسال، هم onHand و هم reserved کاهش یابند.
  • برای جلوگیری از oversell، فقط یک findFirst و سپس update کافی نیست؛ ردیف balance را در transaction قفل کنید (یا optimistic concurrency/Serializable با retry پیاده کنید).
  • هر فرمانی که retry می‌شود idempotency key بگیرد؛ درخواست تکراری نباید دو رسید یا دو movement بسازد.

طرح الگوریتم reserve در سرویس (نمونه‌ی مفهومی؛ اعتبارسنجی tenant، وضعیت سفارش و خطاها هم باید اضافه شود):

await prisma.$transaction(async (tx) => {
  // ابتدا ردیف balance را با upsert ایجاد/تضمین کنید.
  await tx.stockBalance.upsert({
    where: { warehouseId_productId: { warehouseId, productId } },
    create: { companyId, warehouseId, productId, onHand: 0, reserved: 0 },
    update: {},
  });

  // در PostgreSQL ردیف را قفل کنید تا دو درخواست هم‌زمان oversell نکنند.
  const [balance] = await tx.$queryRaw`
    SELECT "onHand", "reserved" FROM "StockBalance"
    WHERE "companyId" = ${companyId}
      AND "warehouseId" = ${warehouseId}
      AND "productId" = ${productId}
    FOR UPDATE
  `;
  if (!balance || balance.onHand.minus(balance.reserved).lt(quantity)) {
    throw new ConflictException("موجودی قابل‌دسترس کافی نیست");
  }

  await tx.stockBalance.update({
    where: { warehouseId_productId: { warehouseId, productId } },
    data: { reserved: { increment: quantity } },
  });
  await tx.stockReservation.create({
    data: { companyId, warehouseId, productId, salesOrderLineId, quantity },
  });
}, { isolationLevel: Prisma.TransactionIsolationLevel.Serializable });

نوع خروجی $queryRaw را در کد واقعی تایپ کنید و با نسخه‌ی client/driver تست کنید. اگر transaction روی serialization conflict شکست خورد، retry محدود با backoff داشته باشید؛ retry نامحدود نکنید.

12 فرآیند خرید

  1. Draft: تأمین‌کننده، انبار مقصد و ردیف‌های کالا/مقدار/قیمت وارد می‌شود. مبلغ‌ها در سرور از روی ردیف‌ها محاسبه می‌شوند، نه از total مورد اعتماد کلاینت.
  2. Approve: نقش مجاز سفارش را تأیید می‌کند. بعد از تأیید، تغییرهای حساس با revision یا لغو و ایجاد نسخه‌ی جدید انجام شوند.
  3. Receive: رسید کالا می‌تواند جزئی باشد. برای هر ردیف کنترل کنید مقدار دریافتی از باقیمانده‌ی سفارش بیشتر نشود. رسید، balance و movement در یک transaction ثبت شوند.
  4. Supplier invoice: مبلغ، ارز، مالیات و شماره‌ی فاکتور با سفارش/رسید تطبیق داده شود؛ invoice خارجی را با شماره‌ی داخلی ERP یکی فرض نکنید.
  5. Pay: پرداخت به یک یا چند فاکتور allocate شود؛ مبلغ تخصیص‌یافته از مانده‌ی فاکتور بیشتر نشود.

Transitionهای مجاز را صریح کنید و تغییر وضعیت مستقیم از endpoint عمومی ندهید:

DRAFT → APPROVED → PARTIALLY_RECEIVED → RECEIVED
   └──────────────→ CANCELLED  (فقط در صورت نداشتن دریافت ناسازگار)
رسید خرید باید یک GoodsReceipt و GoodsReceiptLine واقعی بسازد؛ فقط زیادکردن عدد موجودی کافی نیست. شماره سند، کاربر، زمان، انبار، مقدار و ارتباط با ردیف سفارش برای برگشت/ممیزی لازم‌اند.

13 فرآیند فروش

  1. Draft: مشتری، انبار، ارز، قیمت‌ها و مالیات انتخاب شوند. قیمت و tax rate نهایی در سمت سرور از policy همان شرکت گرفته شود.
  2. Confirm: credit limit/مجوز تأیید و موجودی قابل‌دسترس بررسی؛ برای کالاهای stock-tracked رزرو ایجاد شود.
  3. Ship: ارسال کامل یا جزئی با SalesShipment ثبت شود؛ رزرو مصرف و balance کم شود؛ movement منفی و در صورت روش perpetual، ثبت بهای تمام‌شده در دفتر انجام شود.
  4. Invoice: فاکتور از داده‌ی سند ارسال/سفارش ساخته شود؛ پس از issue شدن، ویرایش مستقیم ممنوع و اصلاح با credit note/سند معکوس باشد.
  5. Collect: دریافت وجه ثبت و به فاکتور تخصیص داده شود؛ وضعیت فاکتور از روی مجموع allocationها محاسبه شود.
DRAFT → CONFIRMED → PARTIALLY_SHIPPED → SHIPPED
   └──────────────→ CANCELLED  (رزروهای فعال آزاد شوند)

قواعد مهم: انبار، کالا، مشتری و سفارش باید متعلق به همان شرکت باشند؛ مقدار ارسال از مقدار سفارش و رزرو باقیمانده بیشتر نشود؛ ارسال دوباره با همان idempotency key سند دوم نسازد؛ کالا/سفارش نهایی‌شده با حذف یا update خام پاک نشود.

در تابع posting:

  • همه‌ی حساب‌ها باید فعال و متعلق به شرکت سند باشند؛ ارز و دوره‌ی مالی باید باز باشد.
  • از Decimal محاسبه کنید، rounding policy را صریح کنید و مانده را بر اساس ارز/precision شرکت نگه دارید.
  • قبل از تغییر status به POSTED، sum(debit) === sum(credit) و تعداد خطوط معتبر باشد؛ برای جمع مبالغ از tolerance تصادفی float استفاده نکنید.
  • ترکیب ثبت journal و تغییر status سند در یک transaction و با unique source key انجام شود تا صدور مجدد دوباره ثبت مالی نسازد.
  • برای تراز آزمایشی، دفتر کل، AR/AP aging و cash report فیلتر تاریخ/شعبه و قواعد تاریخ ثبت را تعریف کنید.
نرخ مالیات را در کد hardcode نکنید. نگه‌داری tax code، اعتبار زمانی نرخ، شماره‌گذاری قانونی اسناد، ارز چندگانه و بستن دوره در نسخه‌ی واقعی باید بر اساس کشور/حسابداری شرکت طراحی شود.

export async function apiFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  const response = await fetch(`/api/v1${path}`, {
    ...init,
    credentials: "include",
    headers: {
      "Content-Type": "application/json",
      ...init.headers,
    },
  });

  if (!response.ok) {
    const body = await response.json().catch(() => null);
    throw new ApiError(response.status, body);
  }
  if (response.status === 204) return undefined as T;
  return response.json() as Promise<T>;
}

17 گزارش، ممیزی و فایل‌ها

گزارش‌های MVP: مانده و گردش موجودی به تفکیک کالا/انبار، فروش بر اساس بازه/مشتری/کالا، خرید بر اساس تأمین‌کننده، فاکتورهای سررسیدشده، AR/AP aging، cash summary و trial balance. Queryهای گزارش باید company-scoped، دارای محدودیت بازه‌ی زمانی و index متناسب باشند.

Audit log: برای loginهای حساس، تغییر نقش/قیمت، تأیید/لغو سند، اصلاح انبار، صدور فاکتور، دریافت/پرداخت و تنظیمات شرکت ثبت کنید: actor، company، action، entity، زمان، request ID و قبل/بعدِ فیلدهای مجاز. رمز، token و اطلاعات بانکی/شخصی حساس را log نکنید.

فایل پیوست: فایل فاکتور، تصویر کالا و اسناد را در object storage خصوصی (مثلاً S3-compatible) قرار دهید؛ در DB فقط metadata، مالکیت، MIME، اندازه و کلید ذخیره شود. دانلود با permission و signed URL کوتاه‌عمر انجام شود؛ MIME و حجم ورودی validate و اسکن شود.

برای ایمیل، webhook و اعلان، از transaction اصلی خارج شوید: رویداد را در outbox همان transaction ذخیره کنید و worker با retry کنترل‌شده تحویل دهد. ارسال ایمیل نباید transaction ثبت فروش را خراب کند.

21 استقرار، مانیتورینگ و پشتیبان‌گیری

  • Local: Docker Compose برای Postgres و Nx serve برای اپ‌ها.
  • Production: build immutable برای API و UI؛ UI پشت Nginx/CDN و API پشت reverse proxy با HTTPS؛ دیتابیس managed/private ترجیح دارد.
  • Migration: در release به‌صورت مرحله‌ی کنترل‌شده و قبل/بعد از deploy اجرا شود؛ migration مخرب را با الگوی expand/contract و سازگاری نسخه‌ها انجام دهید.
  • Health: /health/live برای زنده بودن process و /health/ready برای readiness وابستگی‌های لازم؛ health endpoint اطلاعات حساس ندهد.
  • Logs/metrics: log ساختاریافته با request ID، latency، نرخ خطا و metricهای دیتابیس؛ PII/رمز/توکن در log ممنوع. برای Prometheus/Grafana از secret امن و image version پین‌شده استفاده کنید.
  • Backup: backup رمزگذاری‌شده، retention مشخص و PITR در صورت نیاز؛ restore را به‌صورت دوره‌ای در محیط جدا تمرین کنید. backup آزمایش‌نشده تضمین بازیابی نیست.
  • Docker: از root اجرا نکنید، imageها را pin کنید، dependency و فایل env را در image نریزید؛ Dockerfile تولیدی Nx را با output واقعی build خود بررسی کنید، چون مسیر dist به bundler/config وابسته است.
docker-compose و رمزهای ساده‌ی راهنمای توسعه، deployment production نیستند. admin/admin، Grafana بدون رمز یا latest در سرویس حساس نگذارید.

23 معیار تحویل ERP MVP

نسخه را وقتی MVP بنامید که این موارد قابل اجرا و تست باشند:

  • کاربر وارد می‌شود، شرکت/شعبه‌ی مجاز را انتخاب می‌کند و منوی مطابق permission می‌بیند.
  • محصول، مشتری، تأمین‌کننده و انبار تعریف می‌شوند و داده‌ی شرکت دیگر قابل مشاهده نیست.
  • سفارش خرید تأیید و به‌صورت جزئی دریافت می‌شود؛ مانده‌ی انبار و ledger گردش با رسید هماهنگ‌اند.
  • سفارش فروش موجودی را رزرو می‌کند؛ shipment جزئی مانده را درست کم می‌کند؛ لغو reservation را آزاد می‌کند.
  • صدور invoice و دریافت/پرداخت idempotent است؛ postingهای مالی ترازند و سند posted قابل ویرایش خام نیست.
  • گزارش مانده‌ی انبار، فروش، خرید، AR/AP و trial balance با فیلتر تاریخ/شرکت درست است.
  • تست race condition، rollback، permission، company isolation، migration و مسیر E2E در CI می‌گذرد.
  • هیچ secret واقعی در repo نیست؛ backup/restore، health check و روش انتشار مستند و تمرین‌شده‌اند.
جمع‌بندی: با این گسترش، فایل از «راهنمای نصب Nx + دو اپ خالی» به یک blueprint عملی برای ERP MVP تبدیل شده است: دامنه‌ی واقعی، schema پایه، گردش‌کارهای end-to-end، API، UI، امنیت، حسابداری، تست و انتشار. قدم منطقی بعدی، پیاده‌سازی milestoneهای ۰ تا ۴ در همین ترتیب و تبدیل هر بخش به کد و تست در repo است.
نسخه‌ی توسعه‌یافته‌ی راهنمای Nx Monorepo — مناسب شروع یک ERP قابل توسعه با React، NestJS، Prisma و PostgreSQL. پیش از استفاده‌ی عملی، schema را با Prisma validate کنید و قواعد مالی/مالیاتی را متناسب با کسب‌وکار نهایی بازبینی کنید.

GET {{baseUrl}}/purchasing/orders?page=1&pageSize=25&status=PARTIALLY_RECEIVED

Sales API — سفارش، رزرو و ارسال

ساخت سفارش فروش — POST /sales/orders

{
  "customerId": "{{customerId}}",
  "branchId": "{{branchId}}",
  "warehouseId": "{{warehouseId}}",
  "currency": "AZN",
  "lines": [
    {
      "productId": "{{productId}}",
      "description": "پیچ صنعتی ۱۰ میلی‌متری",
      "quantity": "6.000",
      "unitPrice": "2.50",
      "taxRate": "0.00"
    }
  ]
}

URL: {{baseUrl}}/sales/orders. از پاسخ data.id و data.lines[0].id را به salesOrderId و salesOrderLineId ذخیره کنید. تأیید سفارش body ندارد و باید ۶ واحد رزرو کند:

POST {{baseUrl}}/sales/orders/{{salesOrderId}}/confirm

ثبت ارسال — POST /sales/orders/{{salesOrderId}}/shipments

{
  "number": "SHP-DEMO-001",
  "shippedAt": "2026-10-02T11:30:00.000Z",
  "lines": [
    { "salesOrderLineId": "{{salesOrderLineId}}", "quantity": "6.000" }
  ]
}

بعد از ارسال، GET /inventory/balances را چک کنید: موجودی کل و رزرو باید مطابق shipment کم شوند و یک movement منفی ثبت شود. فهرست سفارش‌های فروش:

GET {{baseUrl}}/sales/orders?page=1&pageSize=25&status=SHIPPED

Finance API — فاکتور، پرداخت و دفتر

ساخت draft فاکتور از سفارش فروش — POST /finance/invoices
سرور باید lineها و مبلغ را از سند مرجع بسازد و total ارسالی از کلاینت را نپذیرد.

{
  "type": "SALES",
  "salesOrderId": "{{salesOrderId}}",
  "customerId": "{{customerId}}",
  "currency": "AZN",
  "issueDate": "2026-10-02",
  "dueDate": "2026-11-01"
}

از پاسخ data.id را به invoiceId ذخیره و فاکتور را صادر کنید؛ این endpoint body ندارد:

POST {{baseUrl}}/finance/invoices/{{invoiceId}}/issue

صدور باید status را به ISSUED تغییر دهد و یک Journal متوازن بسازد. برای پرداخت بخشی از فاکتور:

POST {{baseUrl}}/finance/payments
{
  "direction": "INCOMING",
  "amount": "5.00",
  "currency": "AZN",
  "method": "BANK_TRANSFER",
  "reference": "PAY-DEMO-001",
  "allocations": [
    { "invoiceId": "{{invoiceId}}", "amount": "5.00" }
  ]
}

برای تکمیل چرخه‌ی خرید، بعد از رسید، draft فاکتور تأمین‌کننده را از سفارش خرید بسازید (همان URL POST /finance/invoices):

{
  "type": "PURCHASE",
  "purchaseOrderId": "{{purchaseOrderId}}",
  "supplierId": "{{supplierId}}",
  "currency": "AZN",
  "issueDate": "2026-10-02",
  "dueDate": "2026-10-16"
}

شناسه‌ی پاسخ را در purchaseInvoiceId ذخیره کنید، سپس صادر و بخشی از آن را پرداخت کنید:

POST {{baseUrl}}/finance/invoices/{{purchaseInvoiceId}}/issue
POST {{baseUrl}}/finance/payments
{
  "direction": "OUTGOING",
  "amount": "3.00",
  "currency": "AZN",
  "method": "BANK_TRANSFER",
  "reference": "PAY-VENDOR-DEMO-001",
  "allocations": [
    { "invoiceId": "{{purchaseInvoiceId}}", "amount": "3.00" }
  ]
}

دریافت لیست فاکتورها و پرداخت‌ها:

GET {{baseUrl}}/finance/invoices?page=1&pageSize=25
GET {{baseUrl}}/finance/payments?page=1&pageSize=25

تراز آزمایشی در بازه‌ی انتخابی، بدون body:

GET {{baseUrl}}/finance/reports/trial-balance?from=2026-10-01&to=2026-10-31&currency=AZN

Reports API — گزارش‌های قابل راستی‌آزمایی

GET {{baseUrl}}/reports/overview?from=2026-09-26&to=2026-10-02
GET {{baseUrl}}/reports/sales?from=2026-10-01&to=2026-10-31&groupBy=day
GET {{baseUrl}}/reports/stock-valuation?warehouseId={{warehouseId}}
GET {{baseUrl}}/reports/ar-aging?asOf=2026-10-02

GETها body ندارند. جمع فروش را با invoiceهای صادرشده، ارزش موجودی را با روش costing انتخاب‌شده و AR aging را با مانده‌ی فاکتورهای فروش تطبیق دهید. خروجی گزارش باید فقط داده‌های شرکت فعال را شامل شود.

چک‌لیست هر API: URL/HTTP method درست است؟ body طبق DTO اعتبارسنجی می‌شود؟ پاسخ موفق و خطای 400/401/403/404/409 تست شده؟ شرکت دیگر قابل دسترسی نیست؟ اجرای تکراری سند تکراری می‌سازد؟ اثر دیتابیس، audit و پاسخ API هم‌خوان‌اند؟ نتیجه را کنار test case همان endpoint ثبت کنید.

اجرای سریع پروژه:

cd erp-frontend
npm install

دمو بدون بک‌اند پیش‌فرض است و اطلاعات نمونه را در localStorage نگه می‌دارد. برای اتصال به API واقعی در فایل .env:

VITE_API_MODE=live
VITE_API_BASE_URL=/api/v1
VITE_PROXY_TARGET=http://localhost:3000

بعد از آن npm run dev را اجرا کنید؛ Vite درخواست‌های /api را به Nest proxy می‌کند. صفحه‌ی ورود در حالت mock دمو است؛ در حالت live، endpoint واقعی /auth/login باید accessToken و کاربر را برگرداند. access token فقط در حافظه‌ی اپ نگه‌داری می‌شود.
