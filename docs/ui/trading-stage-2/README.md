# مرحلهٔ دوم — ثبت و مدیریت سفارش‌های پروژه

این تغییر، پنل دوم `/trading` و بخش سفارش‌های صفحهٔ هر پروژه (`/trading/projects/{id}`) را به یک کامپوننت مشترک متصل می‌کند. فرم قدیمی جداگانهٔ ORDER و جدول بدون صفحه‌بندی سفارش در صفحهٔ پروژه حذف شده‌اند تا دو پیاده‌سازی موازی نداشته باشیم. مرحلهٔ اول بدون اضافه‌شدن فیلد جدید حفظ شده است؛ گام‌های بعدی در نمای شش‌گامی همچنان placeholder هستند.

## قابلیت‌های همین نسخه

- انتخاب پروژهٔ واقعی با جست‌وجوی شماره/موضوع و صفحه‌بندی؛ سفارش بدون پروژه ساخته نمی‌شود.
- چند سفارش برای یک پروژه؛ هر سفارش شناسهٔ مستقل و شمارهٔ ثبت سفارش یکتای سراسری دارد.
- فهرست سمت سرور با جست‌وجوی شماره، فیلتر وضعیت و صفحه‌های ۲۵تایی.
- ثبت سند، ویرایش اطلاعات پیش‌نویس، تغییر وضعیت مستقل با دلیل، کنترل نسخه و تاریخچه.
- کنترل خروج از فرم تغییرکرده، حفظ ورودی در خطای شبکه/اعتبارسنجی/نسخهٔ قدیمی، retry فهرست و ارزها.
- حفظ انتخاب ارز حتی خارج از صفحهٔ فعلی نتایج، و حفظ پیش‌نویس هنگام رفت‌وبرگشت میان گام‌ها.
- پروژهٔ بسته/لغوشده فقط خواندنی است؛ سرور هم عملیات جدید و ویرایش را رد می‌کند.
- نمایش و ارسال دقیق مبلغ، بدون Number/parseFloat روی مبلغ و بدون تبدیل ارز.

## فیلدها و منبع داده

| فیلد | منبع فعلی اپ | رفتار |
|---|---|---|
| پروژهٔ مرتبط | `trading.order_registrations.ProjectId` → `trading.projects.Id` | فقط‌خواندنی در فرم؛ قابل جابه‌جایی در ویرایش نیست |
| شمارهٔ ثبت سفارش | `trading.order_registrations.RegistrationNumber` | الزامی، حداکثر ۸۰ کاراکتر، یکتا در کل سیستم |
| تاریخ ثبت سفارش | `trading.order_registrations.RegistrationDate` | الزامی؛ date میلادی در دیتابیس، ورود شمسی در رابط فارسی |
| ارز ثبت سفارش | `CurrencyId` و snapshotهای کد/نام ارز | انتخاب ارز فعال از `reference_data.currencies`، جست‌وجو و paging مستقل |
| مبلغ ثبت سفارش | `trading.order_registrations.RegisteredAmount` | مثبت، `numeric(24,6)`، حداکثر ۱۸ رقم صحیح و ۶ اعشار |
| وضعیت اولیه | `trading.order_registrations.Status` | ایجاد فقط DRAFT؛ تغییر وضعیت فرمان جداست |
| توضیحات سفارش | `trading.order_registrations.Notes` | اختیاری، حداکثر ۲۰۰۰ کاراکتر طبق دیتابیس فعلی |

دلیل ویرایش/تغییر وضعیت در `trading.audit_events.Reason` ثبت می‌شود، نه در توضیحات سفارش. `ExpectedVersion` فیلد فنی فرمان است و قابل ویرایش توسط کاربر نیست.

این نسخه **اطلاعات سند ثبت سفارش** را اجرایی می‌کند، نه کل مدل پیشنهادی ۳۳جدولی. اقلام کالا، HS، واحد/قیمت واحد، مجوزهای جزئی، اینکوترم و روش پرداخت آن طرح در این تغییر به دیتابیس فعلی اضافه نشده‌اند. بانک، تخصیص/دریافت ارز، نرخ ارز، حمل و گمرک نیز در این فرم نیستند. از مقدار ساختگی، مبلغ تخصیص خودکار یا انتقال وضعیت خودکار پروژه استفاده نشده است.

## قواعد ویرایش و وضعیت

- تغییر اطلاعات فقط برای سفارش DRAFT و پروژهٔ باز مجاز است.
- ویرایش سفارش متصل به پروندهٔ ارزی رد می‌شود؛ دادهٔ مالی مرجع بازنویسی نمی‌شود. ویرایش و اتصال FX در تراکنش خود قفل همان ردیف سفارش را می‌گیرند تا بررسی ارتباط با ایجاد هم‌زمان FX رقابت نکند. رفتار lock نیز باید در تست PostgreSQL محیط .NET تأیید شود.
- تعویض ارز به ارز غیرفعال مجاز نیست. اگر همان ارز قبلی غیرفعال شده باشد، ویرایش بدون تعویض ارز snapshot تاریخی را حفظ می‌کند.
- ساخت و ویرایش به همراه ممیزی مربوط در یک SaveChanges ذخیره می‌شوند؛ کلید یکتا و optimistic concurrency موجود دیتابیس استفاده شده است.
- در 409 نسخهٔ قدیمی، فرم پاک نمی‌شود. کاربر می‌تواند مقدار خود را بررسی کند، انصراف دهد، فهرست را به‌روز کند و نسخهٔ تازه را دوباره باز کند؛ بازنویسی اجباری نداریم.
- مسیر عادی: DRAFT → SUBMITTED؛ SUBMITTED → ACTIVE یا SUSPENDED؛ ACTIVE → SUSPENDED؛ SUSPENDED → ACTIVE. لغو از وضعیت‌های غیرنهایی ممکن است.
- اصلاح رو به عقب فقط با علامت صریح اصلاح و دلیل طبق قرارداد قبلی مجاز است. CANCELLED نهایی است؛ حذف فیزیکی یا استفادهٔ مجدد از شمارهٔ آن نداریم.
- چرخهٔ اجرایی فعلی حفظ شده؛ CONFIRMED/EXPIRED طرح آینده به‌جای ACTIVE/SUSPENDED جا زده نشده‌اند.

## API و مجوز

مجوزهای immutable موجود استفاده شده‌اند؛ مجوز محلی، کاربر مدیریتی ساختگی یا دسترسی MRP اضافه نشده است:

| مسیر | مجوز |
|---|---|
| `GET /api/trading/projects/{id}/order-registrations?search=&status=&page=1&pageSize=25` | `trading.order_registration.view` |
| `GET /api/trading/order-registrations/{id}` | `trading.order_registration.view` |
| `GET /api/trading/order-registrations/currencies?search=&page=1&pageSize=25` | `trading.order_registration.manage` |
| `POST /api/trading/order-registrations/resolve-jalali-date` | `trading.order_registration.manage` |
| `POST /api/trading/order-registrations` | `trading.order_registration.manage` |
| `PUT /api/trading/order-registrations/{id}` | `trading.order_registration.manage` |
| `POST /api/trading/order-registrations/{id}/status` | `trading.order_registration.manage` |

ورود به فضای بازرگانی و انتخاب پروژه در UI همچنان `trading.project.view` می‌خواهد. کاربر فقط‌مشاهده، lookup ارز و کنترل‌های نوشتن دریافت نمی‌کند؛ بدون مجوز مشاهدهٔ سفارش هیچ درخواست سفارش/lookup از پنل دوم فرستاده نمی‌شود. مخفی‌کردن UI جای مجوز backend نیست؛ همهٔ endpointها محافظت شده‌اند و تعاریف مجوز موجود از قبل در ماتریس مدیر سیستم هستند.

مبلغ در فرمان ثبت/ویرایش به‌شکل رشتهٔ اعشاری ارسال می‌شود؛ ASP.NET آن را مستقیم به decimal می‌خواند. قرارداد جدید خواندن مبلغ رشته برمی‌گرداند تا اعداد بزرگ‌تر از `Number.MAX_SAFE_INTEGER` و هر شش رقم اعشار در مرورگر دقیق بمانند. قراردادهای قدیمی پاسخ پروژه/ایجاد برای مصرف‌کننده‌های قبلی حفظ شده‌اند؛ جدول جدید از قرارداد خواندن دقیق استفاده می‌کند.

تبدیل شمسی همان تقویم مشترک موجود است؛ endpoint مخصوص سفارش نیاز به مجوز اجرای MRP ندارد. قالب تقویم ورودی هر پیش‌نویس با تغییر زبان وسط ویرایش عوض نمی‌شود تا تاریخ اشتباه تفسیر نشود؛ فرم تازه در زبان انگلیسی ورودی ISO دارد.

## دیتابیس و راه‌اندازی

**این تغییر migration جدید ندارد**؛ جدول‌های اجرایی موجود سفارش، مرجع ارز و ممیزی استفاده شده‌اند. اگر migration مرحلهٔ اول هنوز اعمال نشده، باید قبل از اجرای نسخهٔ جدید طبق روال پروژه اعمال شود. `run-hadron.bat` مرحلهٔ build و migration دارد؛ خطای آن را نادیده نگیرید.

برای رابط واقعی، مشتری/پروژهٔ موجود و ارز فعال مرجع مرکزی لازم است. گزینه‌های نمونهٔ HTML به اپ یا دیتابیس تزریق نشده‌اند.

## HTMLها

- `stage-2.html`: نسخهٔ ساده، بدون نام جدول‌ها.
- `stage-2-annotated.html`: همان فرم با مسیر فعلی و معادل مدل پیشنهادی کنار هر فیلد.
- `hadron-logo-red.svg`: لوگوی رسمی پروژه.

فایل‌ها خروجی React SSR از **خود** `TradingOrderView`, `TradingOrderPickerView`, `TradingOrdersListView` و همان CSS اپ هستند؛ دو فرم مستقل نگهداری نشده‌اند. جدول و ارز/پروژهٔ HTML نمونه‌اند؛ ثبت فقط پیش‌نویس مرورگر را ذخیره می‌کند و دکمه‌های مدیریت ردیف‌های نمونه غیرفعال‌اند. عملیات واقعی فقط در اپ به API وصل‌اند.

از ریشهٔ پروژه، پس از نصب وابستگی‌های frontend:

```bash
npm run export:trading-orders --prefix src/frontend
```

خروجی بسته: `output/trading-stage-2.zip`. بستهٔ مرحلهٔ اول و نمونهٔ گستردهٔ قدیمی تغییر نکرده‌اند.

## بررسی‌ها

- build TypeScript/Vite: موفق؛ هشدار عمومی اندازهٔ chunk موجود است.
- ۳۲۳ تست frontend: موفق.
- ESLint فایل‌های تغییرکردهٔ فرم و workspace: بدون خطا یا هشدار.
- تست مرورگر روی build واقعی اپ با **API mock**: ثبت و ویرایش، جست‌وجو/paging، retry، حفظ انتخاب، CSRF، تبدیل تاریخ، ارسال دقیق مبلغ، 400 و 409 بدون پاک‌شدن ورودی، بازکردن نسخهٔ تازه، تغییر وضعیت، دسترسی فقط‌مشاهده و پروژهٔ بسته، کارکرد همان manager در صفحهٔ واقعی پروژه، نبود UI موازی، تاریخ ISO انگلیسی و تغییر زبان، تطبیق دو HTML و عرض موبایل؛ موفق.
- تست مرورگر مرحلهٔ اول نیز برای جلوگیری از regression اجرا شده و موفق است.
- شش تست integration backend جدید نوشته شده‌اند: paging/پروژه/دقت اعشاری؛ ویرایش/ممیزی/نسخه؛ اعتبارسنجی/یکتایی/چرخه؛ مجوزها/تاریخ/lookup؛ پروژهٔ بسته و ارتباط ارزی؛ ارز غیرفعال و snapshot.
- **build .NET و تست‌های backend در این محیط اجرا نشده‌اند؛ دستور dotnet نصب نیست.** تست مرورگر mock جای تست PostgreSQL و اجرای واقعی API را نمی‌گیرد. قبل از انتشار باید در محیط .NET 10/PostgreSQL تست شوند.

```bash
npm test --prefix src/frontend
npm run build --prefix src/frontend
npm ci --prefix scripts/trading-prototype
CHROMIUM_PATH=/path/to/chrome node scripts/trading-prototype/test-app-stage2.mjs
dotnet test tests/backend/Hadron.Erp.IntegrationTests/Hadron.Erp.IntegrationTests.csproj --filter FullyQualifiedName~TradingTests
```

متغیرهای اتصال integration را به دیتابیس تست مستقل تنظیم کنید؛ این تست‌ها را روی دیتابیس عملیاتی اجرا نکنید.
