معماری کلی — Modular Monolith

همه‌چیز در یک پروسه ASP.NET Core و یک دیتابیس PostgreSQL زندگی می‌کند. «ماژولار» بودن اینجا یک قرارداد معماری است نه یک مرز فیزیکی: هر ماژول پوشه‌ی خودش را دارد و نباید مستقیم به جدول ماژول دیگر بنویسد، ولی همه از یک HadronDbContext مشترک استفاده می‌کنند.

ساختار داخلی هر ماژول — چهار لایه

Api/

  • Minimal API Endpoint ها (*Endpoints.cs)
  • فقط نگاشت Route + RequirePermission(...)
  • ترجمه Exception به HTTP (۴۰۰ / ۴۰۴ / ۴۰۹)
  • هیچ منطق تجاری اینجا نیست

Application/

  • Service ها — ارکستراسیون Use Case
  • Contracts: record های Request/Response
  • Exception های دامنه‌ای اختصاصی
  • اعتبارسنجی + Audit emission

Domain/

  • Entity ها با Constructor خصوصی + متد رفتاری
  • Setter ها private set هستند
  • تغییر وضعیت فقط از راه متد (Edit, ChangeState, …)
  • بدون وابستگی به EF Core

Infrastructure/

  • IEntityTypeConfiguration هر Entity
  • نگاشت به schema.table
  • Check Constraint ها در دیتابیس تعریف می‌شوند
  • Index و Concurrency Token

چهار الگوی تکرارشونده در کل پروژه

۱. Optimistic Concurrency

  • هر Entity یک Version دارد (Concurrency Token)
  • کلاینت باید ExpectedVersion بفرستد
  • عدم تطابق → STALE_VERSION با HTTP ۴۰۹

۲. Deactivate نه Delete

  • هیچ DELETE فیزیکی روی Master Data نیست
  • POST /{id}/deactivate و /reactivate
  • Reactivate اول معتبربودن مراجع را چک می‌کند

۳. Lifecycle State Machine

  • BOM: DRAFT → APPROVED → OBSOLETE
  • Purchase Order: Draft → Approved → Ordered
  • هر انتقال، یک Event در جدول Lifecycle ثبت می‌کند

۴. Post-Commit Audit

  • بعد از موفقیت SaveChanges صدا زده می‌شود
  • شکست Audit فقط Log می‌شود، تراکنش برنمی‌گردد
  • Old/New Snapshot به‌صورت JSON
نکته برای بازنویسی: چون همه ماژول‌ها یک DbContext مشترک دارند، در NestJS بهترین معادلش یک Connection با چند Module است که هر Module فقط Entity های خودش را register می‌کند. اگر بعداً خواستید واقعاً جدا شوید، مرزها از قبل با schema کشیده شده‌اند.

مسیر یک درخواست — از مرورگر تا Service

این ترتیب Middleware ها ترتیب دقیق ثبت‌شده در Program.cs است. جابه‌جا کردنشان معنی امنیتی را عوض می‌کند: مثلاً چک نشست باید بعد از Authentication و قبل از Authorization باشد، وگرنه کاربر Deactivate‌شده تا انقضای کوکی دسترسی دارد.

Fail-Closed — مهم‌ترین تصمیم امنیتی پروژه

ApiPermissionMiddleware روی هر درخواستی که به /api می‌خورد اجرا می‌شود. اگر Endpoint مربوطه هیچ‌کدام از این دو را نداشته باشد، بدون اجرای Handler پاسخ 403 UNREGISTERED_API_PERMISSION می‌گیرد:
  • RequiredPermissionMetadata — یعنی .RequirePermission(...) صدا زده شده باشد
  • IAllowAnonymous — استثناهای صریح (Health, Login, Bootstrap)
یعنی فراموش‌کردن دسترسی روی یک Endpoint جدید، باز شدن دسترسی نیست؛ بلکه از کار افتادن آن Endpoint است.
استثناهای دقیق Middleware: مسیرهایی که اصلاً به Endpoint نگاشت نشده‌اند (۴۰۴) و 405 Method Not Supported دست‌نخورده رد می‌شوند تا قرارداد استاندارد HTTP حفظ شود. /api/auth/logout هم صریحاً استثنا شده تا کاربر همیشه بتواند خارج شود.

موتور MRP — قلب محاسباتی پروژه

الگوی کلیدی اینجا Transactional Outbox است. هیچ ماژولی مستقیم MRP را صدا نمی‌زند؛ فقط داده‌ی خودش را در همان تراکنش در یک جدول صف می‌گذارد و یک Worker جدا آن را برمی‌دارد. این یعنی اگر محاسبه MRP شکست بخورد، ثبت کالا یا رسید انبار هرگز Rollback نمی‌شود.

چه تغییراتی MRP را بیدار می‌کنند

چرخه عمر یک پیام Outbox

۱
PENDING با AvailableAtUtc = now + ۴ ثانیه. این Debounce باعث می‌شود ۵۰ تغییر پشت‌سرهم یک Run بدهند نه ۵۰ تا.
۲
PROCESSING Worker تا ۵۰۰۰ پیام را یک‌جا برمی‌دارد و AttemptCount را زیاد می‌کند.
۳
COMPLETED با RunId مربوطه. اگر snapshot پلن CURRENT از جدیدترین تغییر تازه‌تر باشد، بدون اجرای مجدد COMPLETED می‌شود.
۴
RETRY → PENDING با Backoff نمایی ۲^n × ۵ ثانیه. وقتی AttemptCount به ۳ رسید → FAILED.
۵
WORKER_LEASE_EXPIRED اگر Worker وسط کار بمیرد، اجاره ۱۰ دقیقه‌ای منقضی می‌شود و Worker بعدی پیام را برمی‌گرداند. این همان Idempotency است.

مدل دسترسی — RBAC + Deny + Data Scope

دسترسی‌ها یک‌بار هنگام لاگین محاسبه و به Claim تبدیل می‌شوند، نه در هر درخواست. این کار سریع است ولی یعنی تغییر دسترسی تا رفرش‌شدن Principal اثر ندارد — به همین دلیل فیلد AccessVersion وجود دارد تا نشست‌های قدیمی را باطل کند.

چرا Deny مستقیم لازم است

فرض کنید نقش «کارشناس خرید» دسترسی procurement.purchase_order.approve را دارد. حالا می‌خواهید یک نفر خاص را از این استثنا کنید بدون اینکه نقش را عوض کنید. یک DENY مستقیم روی آن کاربر کافی است. ترتیب اجرا در HadronClaimsPrincipalFactory این است: اول Grant ها اضافه می‌شوند، بعد Deny ها هم حذف می‌کنند و هم یک Claim منفی ثبت می‌کنند — تا در Assertion هم HasClaim(permission) رد شود و هم !HasClaim(deny).
استثنای SystemAdministrator: اگر کاربر این نقش را داشته باشد، کد کلاینت Deny را نادیده می‌گیرد — یعنی permissions = همه ۱۳۵ کد و هیچ permission-deny ثبت نمی‌شود. این نقش با Deny محدودشدنی نیست. آخرین دارنده این نقش هم نه غیرفعال‌شدنی است و نه قابل خلع.

Data Scope — لایه «کدام رکوردها»

RBAC فقط می‌گوید «حق داری رسید انبار ثبت کنی». Data Scope می‌گوید «فقط روی انبار ۳ و ۷». فعلاً فقط دو نوع پیاده شده و بقیه تا وقتی مالکیت رکورد قابل اتکا تعریف شود، به تعویق افتاده‌اند.

نوعمقداروضعیتکجا اعمال می‌شود
ALL—پیاده‌شده WarehouseScope() مقدار null برمی‌گرداند = بدون محدودیت
WAREHOUSE{WarehouseId}پیاده‌شده کوئری‌های Inventory فیلتر می‌شوند؛ در Mutation همه انبارهای درگیر باید در Scope باشند؛ در انتقال داخلی هم مبدأ هم مقصد

۱۰ چیزی که نباید از دست برود

۱. Fail-Closed

  • Guard سراسری که نبودِ متادیتای دسترسی را ۴۰۳ کند
  • یک تست معماری که همه Controller ها را اسکن کند
  • این مهم‌ترین ویژگی امنیتی پروژه است

۲. Optimistic Concurrency

  • Version روی هر Entity
  • ExpectedVersion در هر Request
  • ۴۰۹ STALE_VERSION نه ۵۰۰

۳. Deactivate نه Delete

  • Master Data هرگز پاک نمی‌شود
  • Reactivate مراجع را دوباره اعتبارسنجی می‌کند

۴. Transactional Outbox

  • پیام در همان تراکنش کسب‌وکار
  • Debounce + Coalesce
  • Advisory Lock + Lease + Retry

۵. Snapshot ورودی‌های Run

  • محاسبه روی داده فریزشده
  • بدون آن «چرا این عدد؟» پاسخ ندارد

۶. Calculator خالص

  • ورودی و خروجی فقط رکورد است، بدون I/O
  • به همین دلیل به‌شدت تست‌پذیر است — همین را نگه دارید

۷. Deny بالاتر از Grant

  • ترتیب: Role ∪ Grant − Deny
  • Deny یک Claim منفی هم ثبت می‌کند

۸. AccessVersion

  • ابطال کوکی‌های قدیمی بدون Logout دستی
  • چک در هر درخواست

۹. Data Scope داخل Service

  • نه در Guard — چون به دیتابیس و پارامتر درخواست نیاز دارد
  • در Mutation همه رکوردهای درگیر باید در Scope باشند

۱۰. کدهای خطای پایدار

  • فرانت روی code منطق دارد نه روی متن
  • همان رشته‌ها را حفظ کنید
