# طرح تعاملی بازرگانی — Hadron ERP System

این بسته **۱۱ فایل HTML مستقل با assets مشترک** دارد. طراحی مرحلهٔ اول از دو تصویر ارائه‌شده استخراج شده؛ ظاهر نمونه کپی نشده است. تمام فرم‌ها کنار فیلد، نام جدول/فیلد پیشنهادی و برای انتخاب‌گرها منبع گزینه‌ها را نشان می‌دهند.

> این بسته طرح تعاملی فرانت است، نه قابلیت متصل به دیتابیس. صفحهٔ React اجرایی `/trading`، API، مجوزها و مهاجرت دیتابیس در این تغییر دست‌نخورده‌اند. صفحات مراحل بعد از اول، پیشنهاد مبتنی بر اسکیما هستند و فیلدهایشان هنوز جداگانه توسط مالک تأیید نشده‌اند.

## باز کردن

ZIP را **Extract** کنید و `trading-prototype/index.html` را باز کنید؛ assets باید کنار فایل‌ها باقی بماند. اتصال اینترنت، npm یا سرور برای دیدن فرم‌ها لازم نیست. مستقیماً از داخل ZIP باز نکنید.

برای ذخیرهٔ مشترک مطمئن میان تمام صفحه‌ها، می‌توانید از ریشهٔ ریپو اجرا کنید:

```bash
python -m http.server 5180 --bind 0.0.0.0 --directory docs/ui/trading-prototype
```

سپس در مرورگر **همان کامپیوتر** `http://127.0.0.1:5180` را باز کنید. اگر مرورگر برای URLهای `file://` فضای ذخیرهٔ جدا در نظر بگیرد، خروجی/ورودی JSON در نمای کلی، پیش‌نویس را منتقل می‌کند. مسدود بودن storage به‌صورت خطا نمایش داده می‌شود، نه پیام موفقیت صوری.

## تطبیق مرحلهٔ اول

| فیلد تصویر | طراحی جدید | منبع پیشنهادی |
|---|---|---|
| شمارهٔ داخلی | فقط‌خواندنی، تولید در سرور؛ در نمونه با پیشوند DEMO | `trade_projects.projectNumber` |
| تاریخ شروع / ارجاع | ورودی تاریخ کاری، جدا از تاریخ ثبت | `project_stages.startedAt` با `stage = PROJECT_SETUP` |
| موضوع پروژه | الزامی، کوتاه و مشخص | `trade_projects.titleFa` |
| مشتری | جست‌وجو و انتخاب طرف با نقش CUSTOMER | `trade_projects.customerPartyId` ← `trade_parties.id` + `trade_party_roles.roleCode` |
| کارت بازرگانی | انتخاب کارت موجود؛ نمایش شماره و صاحب کارت | `trade_projects.businessCardId` ← `business_cards.id / cardNumber / partyId` |
| مسئول پیگیری | انتخاب کاربر مرکزی؛ در UI مطابق تصویر الزامی | `trade_projects.responsibleUserId` ← مرجع مرکزی هویت |
| اولویت پروژه | طبق درخواست قبلی از فرم حذف شده | `priorityCode` هنوز در اسکیما هست؛ حذف مدل در این کار انجام نشده |
| وضعیت اولیه | فقط‌خواندنی و مطابق پیش‌فرض مدل: DRAFT | `trade_projects.status` |
| توضیحات | یادداشت کلی پرونده؛ یادداشت مرحله جدا و اختیاری | `trade_projects.notes` و `project_stages.notes` |

افزوده‌ها: خلاصهٔ کالا، تأمین‌کننده و مهلت هدف اختیاری؛ عنوان انگلیسی و یادداشت مرحله در بخش بازشونده. شناسنامهٔ کنار فرم شامل کد هشت‌رقمی، صدور/انقضا، قفل، تاریخ ثبت و ثبت‌کننده است. این‌ها ورودی عادی کاربر نیستند.

وضعیت «در انتظار ثبت سفارش» تصویر بدون فرمان انتقال به مدل تحمیل نشده است. مدل DRAFT را پیش‌فرض می‌گیرد. ثبت خودکار سفارش هنوز قرارداد عملیاتی و API تأییدشده ندارد؛ این نمونه آن را اجراشده جلوه نمی‌دهد. خطای PERMISSION_DENIED تصویر هم یک فیلد کسب‌وکار نیست و بازتولید نشده است.

## تعامل‌هایی که واقعاً کار می‌کنند

- ورود و بررسی الزامی‌ها، قالب عدد، precision/scale مدل و ترتیب تاریخ‌ها.
- تاریخ ورودی استاندارد مرورگر به میلادی؛ نمایش شمسی با `Intl` و منطقهٔ تهران. تقویم ورودی شمسی مستقل ساخته نشده؛ در React نهایی باید از سرویس مرکزی تاریخ استفاده شود.
- ذخیره/بازیابی پیش‌نویس مرورگر، دانلود JSON، ورود پشتیبان با کنترل ساختار و پاک‌کردن فقط دادهٔ نمونهٔ همین بسته.
- جست‌وجوی آفلاین طرفین، فورواردر، کارت و بسته‌بندی با `datalist`؛ در ثبت معتبر، شناسه/کد انتخاب‌شده نگه داشته می‌شود، نه صرفاً نام نمایشی. گزینه‌ها ساختگی و صریحاً نمونه‌اند.
- افزودن/حذف ردیف آزمایشی اقلام، مجوزها، تخصیص، دریافت، وثایق، مسیرها، تسویه‌ها و هزینه‌ها. این حذف هیچ جدول واقعی را تغییر نمی‌دهد.
- محاسبهٔ دقیق با BigInt و مقیاس ثابت ۶ رقم اعشار: جمع ردیف سفارش و سهم هزینه‌ها؛ نرخ‌های ارزی با ۸ رقم اعشار. پیش‌نمایش حاصل ضرب/تقسیم مازاد اعشار را قطع می‌کند؛ سیاست گردکردن نهایی باید در سرویس مالی تعیین شود.
- جلوگیری از تقسیم بر صفر، جمع درصد تخصیص غیر از ۱۰۰، اختلاف مبلغ سهم‌ها و هزینه، و جمع تسویه/پرداخت با ارز متفاوت.
- قفل مرحلهٔ اول: ابتدا یک پروندهٔ نمونه ثبت کنید، سپس «شبیه‌سازی صدور کد و قفل» را بزنید. کد/صدور/انقضای فرضی را وارد کنید؛ مرحلهٔ اول قفل و فرم‌های بعدی قابل بررسی می‌شوند. انقضا از فرمول حدسی ساخته نمی‌شود.
- تا پیش از کد، صفحات بعدی غیرفعال‌اند. دکمهٔ صریح «بررسی فرم در حالت پیش‌نمایش» فقط برای مرور طراحی است، نه مجوز عملیاتی و نه دور زدن قفل واقعی.
- نمایش RTL و واکنش‌گرا، برچسب‌های مرتبط با ورودی، ناوبری صفحه‌کلید، پیام‌های وضعیت و هشدار خروج از فرم تغییرکرده.

## ردیابی داده

- `field-map.json`: نگاشت ۱۹۳ تعریف کنترل به جدول و فیلد واقعی اسکیما؛ ردیف‌های تکرارشونده همین تعریف‌ها را استفاده می‌کنند.
- `assets/data.js`: استخراج مدل و فیلد از `docs/modules/trading/data-map/trading.prisma`، به‌همراه تعریف صفحات.
- `data-sources.html`: تمام ۳۳ مدل را با فیلدهای scalar و محل استفاده در طرح نشان می‌دهد. وجود جدول در این مرجع به معنی ساخت CRUD مستقل برای آن نیست.
- نام جدول از `@@map` گرفته شده و فیلدها همان نام camelCase مدل‌اند؛ فیلدها `@map` جدا ندارند. نام SQL نهایی را نباید بدون تطبیق با مهاجرت EF Core فرض کرد.
- کاربران، ارزها و واحدها از سرویس‌های مرجع مشترک خواهند آمد؛ جدول تکراری برای آن‌ها ساخته نشده است.
- JSON خروجی یک **پیش‌نویس UI گروه‌بندی‌شده** است؛ قرارداد API یا دامپ قابل ورود به PostgreSQL نیست. UUIDهای گزینه‌های نمونه و شناسهٔ اقلام نمونه اعتبار دیتابیسی ندارند.

## موارد لازم برای اتصال واقعی به `/trading`

۱. پیاده‌سازی این فرم‌ها در React با shell، UI primitives، i18n و سرویس مرکزی تاریخ موجود؛ صفحات اجرایی در این کار تغییر نکرده‌اند.
۲. endpointهای مجاز، دادهٔ واقعی انتخاب‌گرها، جست‌وجوی صفحه‌بندی‌شده و مدیریت انتخاب رکورد اصلی: چند سفارش، پروندهٔ ارزی و محموله. این نمونه در هر صفحه فقط یک رکورد اصلی منتخب را پیش‌نمایش می‌کند.
۳. ثبت تراکنشی پرونده + مرحله + ممیزی، ID/FK واقعی، نسخهٔ هم‌زمانی، server validation، کنترل یکتایی کد و مجوزهای default-deny.
۴. قفل و gate معتبر در سرور؛ محاسبات مالی نهایی با decimal؛ تعیین سیاست گردکردن. قفل مرورگر هرگز کنترل امنیت نیست.
۵. تعریف هزینه‌های اجباری هر مرحله و gate تکمیل از `cost_types.isMandatory / stage`؛ در این نمونه هیچ نوع هزینه‌ای بدون تأیید کسب‌وکار اجباری فرض نشده است.
۶. سرویس اسناد و آپلود واقعی برای `project_documents.storageKey`؛ در این نسخه فایل به سرور آپلود نمی‌شود.
۷. تعیین تکلیف اختلاف‌های مدل: `priorityCode` باقی‌مانده، `order_registrations.bankPartyId` باقی‌مانده، دریافت سه‌حالته و منابع مالکیت مشتری/تأمین‌کننده. اسکیما و بک‌اند در این تغییر بازطراحی نشده‌اند.

## ساخت مجدد و تست

از ریشهٔ ریپو:

```bash
python scripts/trading-prototype/build.py
node --check docs/ui/trading-prototype/assets/app.js
npm ci --prefix scripts/trading-prototype
```

برای تست مرورگر، Chromium/Chrome محلی لازم است؛ مسیر فایل اجرایی را مشخص کنید:

```bash
CHROMIUM_PATH=/path/to/chromium npm test --prefix scripts/trading-prototype
```

PowerShell:

```powershell
$env:CHROMIUM_PATH = 'C:\Program Files\Google\Chrome\Application\chrome.exe'
npm test --prefix scripts/trading-prototype
```

مولد ۱۱ صفحه، قرارداد نگاشت و دادهٔ مدل را می‌سازد، سپس کل پوشه را در `output/trading-prototype.zip` قرار می‌دهد. تست‌ها با سرور موقت محلی اجرا می‌شوند؛ به API پروژه یا دیتابیس متصل نیستند. باینری مرورگر و node_modules داخل ZIP نیستند.

```bash
git fetch origin
```
