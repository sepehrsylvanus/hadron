## ۱) خلاصهٔ مدیریتی

مدل دادهٔ بازرگانی از صفر و بر پایهٔ هشت مرحلهٔ عملیاتی (پرونده → ثبت سفارش → ارز → بیمه/بازرسی → حمل → گمرک → رفع تعهد → هزینه) طراحی شد؛ نه بر پایهٔ نقشهٔ HTML قبلی. نتیجه **۳۳ جدول، ۲۱ enum، ۵۱۲ ستون و ۱۰۲ رابطه** است که با `prisma validate` بدون خطا تأیید شد. نقشهٔ تعاملی HTML هم با همین مدل بازنویسی شد و اکنون ۳۳ کارت، ۱۱ زیرگروه و نمایش‌گر متن کامل اسکیما دارد. هیچ خط کدی از بک‌اند یا فرانت‌اند تغییر نکرد.

## ۷) تصمیم‌های نیازمند تأیید

1. **اولویت پرونده**: به‌جای فیلد ساختاری، `priorityCode` از دیکشنری — چون در یادداشت‌ها «اولویت پروژه حذف شود» بود.
2. **`ReceiptStatus` سه‌حالته** (`NOT_RECEIVED / PARTIAL / RECEIVED`) — اگر فقط دو حالت بخواهی، `PARTIAL` حذف می‌شود.
3. **`FxFile` مستقل از `OrderRegistration`** — ارز به پرونده می‌چسبد، نه به ثبت سفارش؛ اتصال اختیاری از `fx_allocations` به ردیف سفارش هست.
4. **مشتری و تأمین‌کننده در `TradeParty`** — اگر ماژول فروش/خرید جدا نگه می‌دارد، این‌ها باید فقط ارجاع باشند.

## ۸) ریسک‌ها و کارهای باز

- بک‌اند فعلی (`TradingConfiguration.cs`) فقط ۱۱ جدول را با CHECK پوشش می‌دهد؛ مهاجرت EF Core نوشته نشده است.
- `EightDigitCode` / `IsLocked` / انقضا در کد فعلی وجود ندارد.
- ماژول‌های `Fx` و `Commitment` در بک‌اند و فرانت‌اند نیستند.
- تاریخ شمسی فقط نمایشی است؛ ذخیره میلادی — باید در لایهٔ UI یکسان شود.
- قواعدی که Prisma نمی‌تواند بیان کند (قفل کد ۸ رقمی، پل زدن مرحله‌ها، محاسبهٔ نرخ، ممیزی فقط‌افزودنی، ممنوعیت حذف سخت) باید در سرویس یا تریگر دیتابیس پیاده شوند.
